## 1. The headline: the manifest stopped both binaries from starting

`beckon.exe --version` produced nothing at all. `beckon installed` returned
**0 lines in 15 ms**, against a documented catalog-scan cost of 370–500 ms —
which is what made it obvious the process was not running rather than running
badly.

Run through `cmd /c` to capture the real stream:

```
The application has failed to start because its side-by-side configuration
is incorrect. Please see the application event log or use the command-line
sxstrace.exe tool for more detail.
```

Application event log, provider `SideBySide`, id 59:

```
Activation context generation failed for
"C:\Users\kln\dev\beckon\target\debug\beckon.exe".
Error in manifest or policy file "...beckon.exe" on line 41.
Invalid Xml syntax.
```

**Cause:** three XML comments in `beckon.exe.manifest` contained `--`, which
is illegal inside an XML comment. Windows' SxS parser rejects the entire
manifest, and with it the process.

**This repo already knew.** `examples/windows/serve/beckon-serve.xml` opens
with *"XML comments cannot contain a double hyphen"* and works around it by
spelling the log option out in prose. The final review wave then wrote
``--log``, `Documented, not measured --` and ``no `CP_ACP` -- every string``
into manifest comments.

### What did not catch it

| Gate | Why it passed |
|---|---|
| Three code reviews | One *did* run an XML parser — before the wave that introduced the hyphens |
| The CI byte-search gate (Task 7) | Passes by design: the strings it looks for really are present |
| `x86_64-pc-windows-gnu` cross-check | Cannot see the manifest at all; `build.rs` embeds it for `-msvc` only |
| The host test suite | 188 tests, none of which start a Windows binary |

Fixed in `8f27b40`, together with the gate that does catch this class: **run
the built binary.** One process start, console subsystem only —
`beckon-serve.exe` answers `--version` with a `MessageBox`, which hangs a
runner with no desktop (observed here: it timed out in session 0).

Verified after the fix: `beckon.exe --version` → `beckon 0.7.0`, exit 0;
`beckon installed` → **122 lines**; zero new `SideBySide` events.

Read back out of the built binaries with Windows' own `FindResource`
(`LOAD_LIBRARY_AS_DATAFILE`, id 1, type 24) — not a byte search, so this
closes the hole Task 7's CI gate admits to.

| | `beckon.exe` | `beckon-serve.exe` |
|---|---|---|
| RT_MANIFEST present | yes, 3495 bytes | yes, 3495 bytes |
| `Microsoft.Windows.Common-Controls` | yes | yes |
| `PerMonitorV2` | yes | yes |
| `asInvoker` | yes | yes |
| `dpiAware` before `dpiAwareness` | yes | yes |

**PE subsystem unchanged**, which the manifest could have disturbed and did
not: `beckon.exe` = 3 (console), `beckon-serve.exe` = 2 (GUI). Matches what
`CLAUDE.md` recorded on 2026-08-11.

## 3. Hot-path cost of the manifest: none, measured with a control

The final review flagged that `beckon.rc` compiles into *every* binary, so the
one-shot `beckon <id>` path now resolves a comctl32 v6 activation context at
process start — on a path with a 50 ms budget and a documented 443→57 ms
optimisation history — and that nobody had re-measured it.

A/B on the same source: strip the manifest line from `beckon.rc`, rebuild,
measure; restore, rebuild, measure. Medians of 7 runs each, debug profile.

| | no manifest | with manifest | delta |
|---|---|---|---|
| `--version` (process-start floor) | 22.9 ms | 22.8 ms | **0.0 ms** |
| `resolve Terminal` | 307.6 ms | 309.4 ms | **+1.8 ms** |

**The control ran first and both builds started cleanly** — without that, a
harness that measures a non-starting process reads as a suspiciously fast
result, which is exactly the trap section 1 fell into before the fix.

**Caveat, stated because it matters:** these are **debug** builds. They are
not comparable to the 57 ms release figure in `CLAUDE.md`; only the *delta* is
meaningful, and the delta is inside the noise.

## 4. Environment notes worth keeping

- `~/.ssh/config` on the dev Mac carries `Include ~/.colima/ssh_config`, and
  every `ssh`/`scp` died with *"Operation not permitted"*. **Re-diagnosed
  2026-08-11 and the first reading was wrong:** it is not TCC. `~/.colima` is
  a symlink to `/Volumes/ssd/colima`, so the Include dangles whenever that
  volume is unmounted, and the message merely looks like a permission denial.
  With the SSD mounted, plain `ssh a14` and `scp` work with no flags at all;
  `colima` itself does not need to be running. Check `ls -d /Volumes/ssd`
  before reaching for the workaround (strip the Include into a temp config
  and pass `-F`).
- Plain `ssh a14 'powershell -Command "..."'` has its quoting destroyed.
  **This one is unrelated to the SSD and is still required**, re-tested
  2026-08-11 with the volume mounted: `-Command` still arrives mangled.
  `-EncodedCommand` with base64 UTF-16LE is the fix, and on this Mac
  `iconv -f UTF-8 -t UTF-16LE file | base64 | tr -d '\n'` is more reliable
  than the python one-liner (python3.14 here produced empty output silently,
  and `pyexpat` is blocked by system policy, so local XML validation is not
  available either — part of why the malformed manifest survived to hardware).
- `Start-Process` does **not** inherit `Set-Location`. A background build
  started that way ran in the wrong directory and produced a 0-byte log.

# Session-1 pass — 2026-08-11, same machine

Route: a scheduled task named `a14probe`, principal a **SID**
(`S-1-5-21-…-1001`), `-LogonType Interactive`,
`New-ScheduledTaskSettingsSet -AllowStartIfOnBatteries`. Payload delivered as
`-EncodedCommand`, output through a `.bat` redirect to a file.

**Control run first, as always:** the harness reported `session=1`,
`desktop-visible=True`, virtual screen `1280x800`. Without that, everything
below would be indistinguishable from a session-0 false negative.

**Display was at 100 % scale** (`GetDpiForSystem = 96`). Nothing at 150 % is

|---|---|

## 7. `lfMessageFont` — the spec's claim, confirmed

```
lfMessageFont.lfFaceName = 'Segoe UI'
lfMessageFont.lfHeight   = -12
lfMessageFont.lfWeight   = 400
iCaptionHeight = 22   iScrollWidth = 17   iMenuHeight = 19
SM_CXSMICON = 16      SM_CXICON = 32
```

`SPI_GETNONCLIENTMETRICS` returns **plain Segoe UI at 9 pt**, not Segoe UI
Variable — exactly as §B.3 of the spec says, now measured rather than cited.

## 8. Font families — the spec was WRONG, and instructively

§B.3 claims Segoe UI Variable exposes **nine** GDI family names,
{Small, Text, Display} × {—, Light, Semib}, with "Semib" truncated to fit
`lfFaceName`'s 32-wchar buffer.

Measured: **twelve**, {Small, Text, Display} × {—, Light, Semibold,
Semilight} — the Semilight axis was missed entirely. And **the truncation is
not uniform**:

```
Segoe UI Variable Text Semibold     <- full, 31 chars
Segoe UI Variable Display Semib     <- truncated
Segoe UI Variable Small Semibol     <- truncated
Segoe UI Variable Text Semiligh     <- truncated
```

So code keyed on the "Semib" spelling finds the Display variant and **misses
the Text one**. Confirmed by the round trip that matters:

```
requested='Segoe UI Variable Text Semib'   got='Arial'     <- silent substitution
requested='Segoe UI Variable Text Semibold' got=(exact)
requested='This Font Does Not Exist'       got='Arial'     <- control
```

The control proves the substitution detector works. This is precisely why the
spec requires a `SelectObject` → `GetTextFace` round trip: `CreateFontW`
succeeded for the wrong name and quietly handed back Arial.

Also confirmed present and exact: `Segoe UI Variable Text` / `Small` /
`Display`, `Segoe Fluent Icons`, `Segoe MDL2 Assets`.

## 9. `caps_probe` — four measurements, all PASS, with a live control

```
RESULT 1: PASS - the injected chord fired our own RegisterHotKey
RESULT 2: PASS - the burst does not open Start
  CONTROL (bare Win tap): Start opened -> foreground SearchHost.exe
RESULT 4: PASS - injected VK_CAPITAL flipped the toggle (0 -> 1),
                 so caps_tap = "capslock" is implementable
RESULT 6: SendInput of 8 strokes took 3941 us  (~3.9 ms)
```

RESULT 1 is the gate the entire Caps-alias design rests on. RESULT 2's control
fired — a bare Win tap really did open Start in the same run — which is the
only thing that separates "the burst is safe" from "the detector is broken".
3.9 ms is 1.3 % of the 300 ms `LowLevelHooksTimeout`.

## 10. The settings window opens and is drivable under the manifest

`settings_probe` found the tray window, opened settings (`760x560` at 96 DPI,
which is what `scale()` yields at 100 %), enumerated 21 child controls, and
drove an edit character by character. The manifest did not break the window.

The controls listed are still the pre-redesign set (`Keyboard` group box,
three tap radios) — correct, because Landing 1 deliberately does not touch
the layout.
