## 1. The headline: the manifest stopped both binaries from starting

`beckon.exe --version` produced nothing at all. `beckon installed` returned
**0 lines in 15 ms**, against a documented catalog-scan cost of 370–500 ms —
which is what made it obvious the process was not running rather than running
badly.

Run through `cmd /c` to capture the real stream:

```
The application has failed to start because its side-by-side configuration
is incorrect. Please see the application event log or use the command-line
sxstrace.exe tool for more detail.
```

Application event log, provider `SideBySide`, id 59:

```
Activation context generation failed for
"C:\Users\kln\dev\beckon\target\debug\beckon.exe".
Error in manifest or policy file "...beckon.exe" on line 41.
Invalid Xml syntax.
```

**Cause:** three XML comments in `beckon.exe.manifest` contained `--`, which
is illegal inside an XML comment. Windows' SxS parser rejects the entire
manifest, and with it the process.

**This repo already knew.** `examples/windows/serve/beckon-serve.xml` opens
with *"XML comments cannot contain a double hyphen"* and works around it by
spelling the log option out in prose. The final review wave then wrote
``--log``, `Documented, not measured --` and ``no `CP_ACP` -- every string``
into manifest comments.

### What did not catch it

| Gate | Why it passed |
|---|---|
| Three code reviews | One *did* run an XML parser — before the wave that introduced the hyphens |
| The CI byte-search gate (Task 7) | Passes by design: the strings it looks for really are present |
| `x86_64-pc-windows-gnu` cross-check | Cannot see the manifest at all; `build.rs` embeds it for `-msvc` only |
| The host test suite | 188 tests, none of which start a Windows binary |

Fixed in `8f27b40`, together with the gate that does catch this class: **run
the built binary.** One process start, console subsystem only —
`beckon-serve.exe` answers `--version` with a `MessageBox`, which hangs a
runner with no desktop (observed here: it timed out in session 0).

Verified after the fix: `beckon.exe --version` → `beckon 0.7.0`, exit 0;
`beckon installed` → **122 lines**; zero new `SideBySide` events.

## 4. Environment notes worth keeping

- `~/.ssh/config` on the dev Mac carries `Include ~/.colima/ssh_config`, and
  every `ssh`/`scp` died with *"Operation not permitted"*. **Re-diagnosed
  2026-08-11 and the first reading was wrong:** it is not TCC. `~/.colima` is
  a symlink to `/Volumes/ssd/colima`, so the Include dangles whenever that
  volume is unmounted, and the message merely looks like a permission denial.
  With the SSD mounted, plain `ssh a14` and `scp` work with no flags at all;
  `colima` itself does not need to be running. Check `ls -d /Volumes/ssd`
  before reaching for the workaround (strip the Include into a temp config
  and pass `-F`).
- Plain `ssh a14 'powershell -Command "..."'` has its quoting destroyed.
  **This one is unrelated to the SSD and is still required**, re-tested
  2026-08-11 with the volume mounted: `-Command` still arrives mangled.
  `-EncodedCommand` with base64 UTF-16LE is the fix, and on this Mac
  `iconv -f UTF-8 -t UTF-16LE file | base64 | tr -d '\n'` is more reliable
  than the python one-liner (python3.14 here produced empty output silently,
  and `pyexpat` is blocked by system policy, so local XML validation is not
  available either — part of why the malformed manifest survived to hardware).
- `Start-Process` does **not** inherit `Set-Location`. A background build
  started that way ran in the wrong directory and produced a 0-byte log.

## 8. Font families — the spec was WRONG, and instructively

§B.3 claims Segoe UI Variable exposes **nine** GDI family names,
{Small, Text, Display} × {—, Light, Semib}, with "Semib" truncated to fit
`lfFaceName`'s 32-wchar buffer.

Measured: **twelve**, {Small, Text, Display} × {—, Light, Semibold,
Semilight} — the Semilight axis was missed entirely. And **the truncation is
not uniform**:

```
Segoe UI Variable Text Semibold     <- full, 31 chars
Segoe UI Variable Display Semib     <- truncated
Segoe UI Variable Small Semibol     <- truncated
Segoe UI Variable Text Semiligh     <- truncated
```

So code keyed on the "Semib" spelling finds the Display variant and **misses
the Text one**. Confirmed by the round trip that matters:

```
requested='Segoe UI Variable Text Semib'   got='Arial'     <- silent substitution
requested='Segoe UI Variable Text Semibold' got=(exact)
requested='This Font Does Not Exist'       got='Arial'     <- control
```

The control proves the substitution detector works. This is precisely why the
spec requires a `SelectObject` → `GetTextFace` round trip: `CreateFontW`
succeeded for the wrong name and quietly handed back Arial.

Also confirmed present and exact: `Segoe UI Variable Text` / `Small` /
`Display`, `Segoe Fluent Icons`, `Segoe MDL2 Assets`.

## 12. The display is at 150 %, not 100 % — §5 and §10 are wrong

This is the finding that reorders everything else, so it goes first.

| reading | value | who read it |
|---|---|---|
| `GetDpiForWindow(settings window)` | **144** | `settings_probe`, per-monitor-aware |
| `GetDpiForSystem()` | **144** | `settings_probe`, per-monitor-aware |
| panel native mode (EDID, `WmiMonitorListedSupportedSourceModes`) | **1920x1200** | WMI, DPI-independent |
| `Screen.AllScreens[0].Bounds` | **1280x800** | PowerShell, DPI-**unaware** |

1920 / 1280 = 1.5 exactly. The scale factor falls out of two numbers that
never pass through `settings_probe` at all, so it does not depend on
trusting the probe.

§5 above records *"Display was at 100 % scale (`GetDpiForSystem = 96`)"* and
*"virtual screen `1280x800`"* in the same breath. Those two lines are the
same measurement disagreeing with itself: `1280x800` **is** the 150 %
virtualization of the panel's `1920x1200`. The `96` came from the PowerShell
harness, which §6 of this very file records as `UNAWARE` — and
`GetDpiForSystem` returns a flat 96 to an unaware process by design. The
harness measured its own awareness, not the display.

**Consequence for §10**: the `760x560` window recorded there is the
virtualized reading of a **`1140x840`** window. `scale(760, 144) = 1140`, so
the window was sized correctly the whole time; the probe was reporting it
divided by 1.5. Nothing was broken, but the number in §10 is in units nobody
declared.

**Consequence for §7, not re-measured here**: `lfMessageFont.lfHeight = -12`,
`iCaptionHeight = 22`, `iScrollWidth = 17`, `iMenuHeight = 19`,
`SM_CXSMICON = 16` and `SM_CXICON = 32` were all read by the same unaware
process, and all six are DPI-awareness-scaled the same way `GetDpiForSystem`
is — see the correction marker in §7 for the full breakdown. -12 is 9 pt at
96 DPI; at this display's real 144 DPI the per-monitor answer from
`SystemParametersInfoForDpi` would be -18. The five metrics would read `33`,
≈26, ≈29, `24` and `48` respectively (x1.5, arithmetic). The face name
(`Segoe UI`) and weight (400) are unaffected — a point size, a face name, and
a weight are not pixel geometry. **Flagged, not measured** — nothing in
Landing 2a re-read any of these six, and `ui_font()` already calls the
ForDpi variant for the font, so that half is a documentation defect and not
necessarily a code one; the five system metrics have no such mitigating
evidence yet.

**The fix, so this cannot recur**: `settings_probe` now calls
`SetProcessDpiAwarenessContext(PER_MONITOR_AWARE_V2)` as the first thing in
`run()` and prints the resulting awareness. It has to, and not only for
tidiness: `GetWindowRect` answers an unaware caller in virtualized pixels
while `LVM_GETITEMRECT` and `BCM_GETIDEALSIZE` come back through
`ReadProcessMemory` and are never virtualized. The unaware run printed a
29 px row next to a 21 px header **in the same block** when the truth is
29 and 31. Two unit systems, one table, no label.

## 13. The numbers Landing 2a's tokens are defined against

All physical pixels, at `GetDpiForWindow = 144`. The 96-DPI column is
`physical / 1.5` and is the unit the token constants are written in.

| what | at 144 DPI | at 96 DPI | source | chosen by |
|---|---|---|---|---|
| ListView row height | **29** | 19.33 | `LVM_GETITEMRECT(0, LVIR_BOUNDS)` | **comctl32** |
| ListView header height | **31** | 20.67 | `SysHeader32` rect, and item 0's `top` | **comctl32** |
| BUTTON height, as laid out | **39** | 26 | `GetWindowRect` | `btn_h = s(26)` |
| BUTTON height, theme's ideal | **33** | 22 | `BCM_GETIDEALSIZE` | **theme** |
| EDIT height (`IDC_COMBO`) | **36** | 24 | `GetWindowRect` | `row = s(24)` |
| COMBOBOX closed height (`IDC_APP`) | **33** | 22 | `GetWindowRect` | **theme** (see below) |
| COMBOBOX selection-field item height | **27** | 18 | `CB_GETITEMHEIGHT(-1)` | **theme** |
| `GetDpiForWindow` | **144** | — | — | display |

Read the last column before using any of these: **five** rows are
theme/comctl32-chosen (comctl32 picks the ListView row and header height;
the theme picks the button's ideal size, the combobox's closed height, and
its item height) and **two** are beckon's own tokens measured back out
(`btn_h = s(26)`, `row = s(24)`) — quoting those two as evidence for the
tokens they came from would be circular.

**The COMBOBOX row is theme-chosen and that is provable from the run.**
`layout` places `IDC_APP` with the same `row` height as everything else in
that column — the two `Static`s and the `Edit` beside it all came back 36 —
and the combo came back **33**. A non-owner-draw combo box snaps its closed
height to an integral item height plus borders, so it overrode the token:
27 + 2*3 = 33. `row = s(24)` is 2 logical px taller than the box the theme
actually draws.

**The BUTTON row is worth an eyebrow.** `btn_h = s(26)` is 39 physical
against an ideal of 33 — four logical pixels of slack. `BCM_GETIDEALSIZE`'s
`cx` also came back well under the placed width (`Add` 42 vs 105 placed,
`Remove` 72 vs 120, `Apply` 55 vs 126), which is expected: ideal `cx` is
text-fit, and beckon places buttons on a grid.

**`LVM_GETCOUNTPERPAGE = 16`** does not reconcile against a 2 px border:
(529 − 31 header) / 29 = 17.2, i.e. 17 full rows fit vertically
(17 × 29 = 493 ≤ 498), and a 2 px client border cannot explain losing a
whole row. The doc's own numbers explain it instead: the three
`LIST_COLUMNS` total **561** physical px (see the consistency check below),
but the list control itself is only **482** wide, so the content overflows
horizontally and comctl32 shows a horizontal scroll bar. That bar eats
vertical space — 498 px minus a scroll bar (`SM_CYHSCROLL`, ≈26 physical px
at this DPI) leaves 472, and `floor(472 / 29) = 16`, exactly the reported
count.

**This is a finding in its own right, not just an arithmetic correction.**
Spec §A.3 predicted "the default size already overflows" for `LIST_COLUMNS`
against the listview's default width, and this run is the first live
confirmation of that at 150 % — the column total (561) exceeding the
control's own width (482) by 79 px is exactly the overflow the spec warned
about, not a hypothetical. Task 6's token table needs the columns narrowed
(or the list widened) to remove the horizontal scroll bar, not just the
row-height numbers above.

> **Fixed, and measured on the same machine — see §17.** On

## 24. A populated `CBS_DROPDOWN` does NOT autocomplete as you type

The claim recorded in `settings_window.rs` — that the control rewrites its own
edit text while you type, and that `CBN_EDITCHANGE` therefore carries stale
text — is **false**, and both halves of the landing's fix were built on it.

`crates/beckon-windows/examples/combo_probe.rs` builds the same control
in-process and subclasses the combo's child EDIT. Typing `Notepad` into a
combo with the shipped styles (`CBS_DROPDOWN | CBS_AUTOHSCROLL | CBS_SORT`,
`CB_SETMINVISIBLE(8)`) gives `N`, `No`, `Not`, … `Notepad`; `CB_GETCURSEL`
stays `-1`; and the child EDIT receives **only** `WM_KEYDOWN` / `WM_CHAR` —
never `WM_SETTEXT`, `EM_REPLACESEL` or `EM_SETSEL`.

Controls, all four of which ran:

- an **empty** combo box, and a **plain EDIT** — identical output;
- **comctl32 v5 vs v6**: the same binary run twice, once as `cargo` built it
  and once with `beckon.exe.manifest` stamped in by `mt.exe`. `DllGetVersion`
  reported **5.82.10586** and **6.16.10586**. Both clean.
- **session 1, real focus, real keystrokes** (`SendInput`, `KEYEVENTF_UNICODE`):
  `foreground is ours: true / focus is on the target: true`, and the subclass
  logs `WM_KEYDOWN` then `WM_CHAR`. Also clean.

**Read `DllGetVersion`, not the module path.** Both comctl32 versions live
under `WinSxS`; the first run of this probe read the path, called v5 "v6", and
reported a control it had not actually run. 5.82 is v5; 6.0/6.16 is v6.

**Session 0 cannot answer this question.** The first run went over plain SSH,
where focus is unobtainable — a control that never runs and a clean result are
indistinguishable there. The probe now prints whether it got the foreground on

## 25. What actually corrupted the App field: `layout` on the keystroke path

`apply_state` runs on every keystroke and ends by calling `layout(hwnd)`, which
re-places every control with `SetWindowPos`. A **populated combo box responds
to being resized by re-synchronising its edit to the closest matching item**,
and it selects the whole string — so the next character replaces all of it.

Measured from outside, polling for transitions instead of taking one late
reading (the character is POSTED, not sent, or the intermediate state is
unobservable):

```
typed 'N' -> field "Narrator"  list "N   not installed"  <<< DISAGREES
     [items=121 cursel=-1 sel=0..8 dropped=0 combo="Narrator"]
     transitions: +332us ""  ->  +737us "N"  ->  +4064us "Narrator"
```

`cursel=-1` and `dropped=0` rule out the list; `combo == field` rules out
`text_of`; `sel=0..8` is a select-all that typing never produces; and the two
steps 3.3 ms apart are a message-loop turn.

Bisected with a temporary in-process trace (removed before commit):

```
WM_APP_EDITED read "N"                     <- the read was always CORRECT
apply_state app: field="N" model="N"       <- equal, so no write
apply_state after shows:  field="N"
apply_state after layout: field="Narrator" <<< HERE
```

Reproduced in isolation by adding that one call to a loop that otherwise
agrees, in the same `combo_probe` run:

```
read-then-write-back loop            -> model "Notepad", field "Notepad"  AGREE
the same loop PLUS layout's SetWindowPos -> model "d",
                                            field "Debuggable Package Manager"
```

`model "d"` is the original 2026-08-11 signature, rebuilt from first
principles.

**Fix:** `Ui::shown_external` — `apply_state` calls `layout` only when the
banner's visibility changed. `layout` depends on the client rect, the DPI and
the banner; the first two already arrive as `WM_SIZE` / `WM_DPICHANGED`.

## 36. `mark_glyph`'s four marks are NOT the same width

`settings_window.rs` claimed *"All four are two columns wide so the note
lines line up"*. That is a **monospace** property, asserted about
`Segoe UI Variable Small`. Each note is built as `glyph + "  " + text`, so
the prefix's advance is exactly where the note text starts:

| prefix | 144 DPI | 96 DPI |
|---|---|---|
| `OK` + 2 spaces | **35 px** | **22 px** |
| `!!` + 2 spaces | 20 px | 14 px |
| `! ` + 2 spaces | 20 px | 13 px |
| `..` + 2 spaces | 18 px | 12 px |
| four spaces (the fix) | 20 px | 12 px |

So `OK` stood **15 px** proud of `!!` at this display's DPI, and the other
three were never equal either — 2 px apart, just close enough that §22 saw
`!!` and `!` align and asked only about `OK`. Swapping `Ok` for two spaces
drops the spread from 17 → 2 px at 144 DPI and 10 → 2 px at 96, i.e. to the
tolerance the shipped marks already had among themselves. **It does not make
the column exact**; only a glyph drawn at a fixed x would, which is the
`NM_CUSTOMDRAW` work spec §B.5 defers.

Two methods, three controls, in `hwpass\GlyphWidth.cs`:

- **Method A** `GetTextExtentPoint32W` on the prefix. **Method B** the
  distance a prefix shifts a bar drawn after it, read out of rendered
  pixels. They agree on all five strings at both DPIs.
- **CONTROL 1** — a face that cannot exist (`Zzz No Such Face`) resolves to
  `Arial`, so the `GetTextFaceW` check discriminates; `Segoe UI Variable
  Small` came back verbatim, so nothing fell back. This is landing 2a's
  lesson 2 applied: only the face name discriminates.
- **CONTROL 2** — the same five strings in `Consolas` come back
  `40 40 40 40 40` at 144 DPI and `28 28 28 28 28` at 96. If Segoe had also
  come back all-equal the probe would be measuring nothing.
- **CONTROL 3** — eight leading spaces shift the bar 40 px where none
  shifts it 0, so the pixel scanner is not stuck.

**Method B was wrong first, and said so in a way that read like a finding.**
It looked for the *first* ink of `prefix + text`, which for a glyph-bearing
prefix is the glyph itself — so it reported 0 or 1 px for every mark and
printed `METHODS DISAGREE`, agreeing only in the one case with no glyph. A
wrong quantity under a confident label is worse than a wrong number. Fixed
before any figure above was taken.

Run in **session 0**, deliberately. These are GDI text metrics taken against
an explicit `lfHeight` in a memory DC — no window, no desktop, and the DPI is
a parameter rather than a reading, so the two rows are computed the same way
from session 0 as they would be from session 1. The thing session 0 could
plausibly break is font availability, and CONTROL 1 is exactly the check for
that. Flagged rather than assumed: if a later pass wants it in session 1, the
probe takes no arguments.

while the App `COMBOBOX` took whatever height the theme snapped it to. §22

## 40. Gate A — the text is safe; the selection is not, and that is fine

Filtering to zero rows flips `Ui::shown_empty`, so `apply_state` calls
`layout`, which `SetWindowPos`es the App `COMBOBOX` — the §7.15 data-loss
mechanism, now reachable by typing rather than only by adding the first row
or removing the last. The design defuses the **0-row** direction (`detail`
goes `None`, so the field is cleared before `layout` runs). The **reverse**
direction was the open question: coming back to ≥1 rows, the field holds text
again when `layout` runs.

```
  SUBJECT pass: App holds text
    before: row=0 App="Notepad" sel=0..0 rows=21
    MODEL says (notes strip):     Registered and working.
    filtered to 0 rows; row=-1 App=""
    after:  row=0 App="Notepad" sel=0..7 rows=21
    MODEL says (notes strip):     Registered and working.
```

**The text is not corrupted, and the model agrees with the screen** both
before and after. What does change is the **selection**: `0..0` becomes
`0..7`, the whole of `Notepad`. That is the resize re-synchronise, and it is
invisible to a text read — this gate only sees it because it reads
`CB_GETEDITSEL` as well as `WM_GETTEXT`. A gate that checked the text alone
would have reported a clean pass and missed it entirely.

**Judged benign, with the reasoning written down so it can be re-judged.**
The hazard a whole-string selection creates is that the next character typed
replaces everything. It is not reachable here: focus is in the *filter* box
at that moment, because typing there is what caused the relayout, and both
routes from there to the App field clear or reset the selection anyway — a
click sets the caret, and tabbing into a combo selects all regardless. It
never reaches the model: `suppress` is true across `apply_state`.

**The control pass earned its place by being misread first.** With the App
field emptied beforehand it came back holding `Notepad`, which looked like
the resize inventing a catalogue entry — the §7.15 signature. The notes strip
refuted it: the model said `Registered and working.` throughout, so the
model's app was never empty. `WM_SETTEXT` into the App combo had not reached
the model at all (the `WM_APP_EDITED` / `app_epoch` deferral discards a read
that `apply_state` has overwritten), and the `Notepad` that reappeared was
`apply_state`'s conditional write correctly repairing the control **from**
the model. Asking the model what it thought — through a control that renders
`row_condition` — is what separated "the resize invented text" from "the
window repaired itself".

Two probe defects were found and fixed before any number above was taken:

- `VK_DOWN` selects the **next** row, not the first, so selection state leaked
  between passes and each pass's result depended on its predecessor's.
  `VK_HOME` is absolute.
- The first version printed no row index, so a `-1` selection during the
  0-row phase was invisible.

```
  PASS: list never emptied, text and selection both untouched
```

`rows=1` under a filter matching nothing **is** the exemption: the selected
row survives, so `st.items` never empties, so `Ui::shown_empty` never flips,
so `layout` — and its `SetWindowPos` on a populated App combo — never runs.
`sel` stays `0..0` where §40 measured it becoming `0..7`. Removing the
whole-string selection beat arguing it could not be consumed.

## 44. Gate B, re-run — and the probe was wrong first

The first re-run reported **FAIL**, and it was the probe, not the code:

```
  SUBJECT (filter "weather", model row 13): select view row 0
    rows=2 selected view row=0 App="Notepad"
  FAIL: view index passed straight through as a model index
```

`rows=2` is the tell. The control run had selected Notepad, so the exemption
kept it on screen, and view row 0 was legitimately Notepad. The probe's
expectation predated the exemption. Corrected to select the **last** visible
row — under `weather` the list is `[Notepad(exempt), Weather]` — so a
pass-through would resolve view row 1 to model row 1, `Calculator`:

```
  SUBJECT (filter "weather"): select the LAST visible row
    rows=1 selected view row=0 App="Weather"
  PASS: view row 0 resolved to model row 13
```

`rows` settles back to 1 because once Weather becomes the selection, Notepad
loses its exemption — self-consistent, and worth stating so the two runs'
differing row counts are not read as instability.

**Worth keeping as a pattern:** a passing gate whose premise has been
invalidated by a design change reports a failure that looks like a
regression. The row count is what distinguished "the mapping broke" from
"the probe is asking last week's question".

# Spec F.5 measured — 2026-08-12, a14, a person at the keyboard

`docs/superpowers/specs/2026-08-11-settings-window-redesign.md` §F.5 ends
*"This table is not shipped until it is measured on a14."* This is that
measurement. Probe `hwpass\CapTable.cs`, run **directly on the machine** —
an SSH shell lands in session 0 where a `WH_KEYBOARD_LL` hook sees no
keystrokes at all, so every result there would be a confident false negative.

Per chord, three independent facts: **SEEN** (the hook callback received the
key-down with the expected modifiers held), **SWALLOWED** (the callback
returned 1), **ACTED** (the foreground window class changed anyway).

## 47. The eight "capturable" chords — confirmed, and by an internal A/B

| chord | SEEN | SWALLOWED | ACTED |
|---|---|---|---|
| `Win+T` | yes | yes | **no** |
| `Win+X` | yes | yes | **no** |
| `Win+D` | yes | yes | **no** |
| `Win+E` | yes | yes | **no** |
| `Win+R` | yes | yes | **no** |
| `Win+Tab` | yes | yes | **no** |
| `Alt+Tab` | yes | yes | **no** |
| `Ctrl+Shift+Esc` | yes | yes | **no** |

F.5 excluded these eight from its "cannot be captured" list on documentary
evidence about PowerToys. That inference is now a measurement.

**The control is better than the one designed for it.** `Win+R` appears
twice in the same run, differing in exactly one variable:

```
CONTROL 1 Win+R, passed through   SEEN=True SWALLOWED=False ACTED=True   -> #32770 (the Run dialog)
Win+R                             SEEN=True SWALLOWED=True  ACTED=False  Progman -> Progman
```

Same chord, same session, same probe: let through it opens the Run dialog,
swallowed it does not. That single pair carries the whole claim that
returning 1 suppresses the shell's own handling.

## 48. `Win+L` — F.5's stated mechanism is WRONG, and it matters

F.5 says the hook sees **nothing, including key-ups**, because the chord is
handled on the Winlogon secure desktop where beckon's hook does not exist.

```
Win+L    SEEN=True  SWALLOWED=True  ACTED=True   Progman -> Windows.UI.Core.CoreWindow
```

**The hook does see it.** The key-down is delivered on the normal desktop
before winlogon acts; what returning 1 cannot do is stop the lock. The
machine locked.

This is not pedantry, it changes the design. F.5's "what the user sees"
column says *"Nothing is recorded"* — and that was true only because the
hook was believed blind. In fact a capture field **would** record `Win+L`
happily, and the user would end up with a binding that can never fire.
**`Win+L` has to be excluded by an explicit block-list at commit time**, not
left to a blindness that does not exist.

`Ctrl+Alt+Del` was deliberately not tested: it shares the secure-desktop
mechanism with `Win+L` and is far more disruptive to a live session. Its row
should now be read as unverified rather than as sharing `Win+L`'s
(disproved) explanation.

## 49. `Win+G` — untested here, for a nameable reason

```
Win+G, swallowed         SEEN=True SWALLOWED=True  ACTED=False
Win+G, passed through    SEEN=True SWALLOWED=False ACTED=False   <- the control
```

The pass-through control is what makes this honest: Game Bar does not open
on a14 **even when the key is let through**, so the swallowed run proved
nothing. Cause found rather than guessed — `Microsoft.XboxGamingOverlay`,
the Game Bar app itself, is not installed (only `XboxGameCallableUI`,
`Xbox.TCUI`, `XboxIdentityProvider` and `XboxSpeechToTextOverlay` are).
`GameDVR_Enabled` is 1, which is a different setting and is why the registry
alone would have misled.

**Recorded as UNTESTED, not as refuted.** Needs a machine with the overlay
installed.

## 50. A contaminated first run, and what fixed it

The first pass scored `CONTROL 2` (`Ctrl+Alt+J`, a chord with no OS meaning
at all) as `ACTED=True`, which would have voided every row. The transition
was `#32770 -> Progman`: the user closing the previous test's Run dialog with
Esc, landing inside the next test's 20-second window.

`FgBefore` was captured the instant a test armed, so **the previous test's
cleanup was scored as this chord's effect**. The fix is a `Settle()` that
waits for the foreground class to hold steady before taking the baseline.
Re-run clean:

```
CONTROL 2 Ctrl+Alt+J   SEEN=True SWALLOWED=True ACTED=False  CASCADIA -> CASCADIA
```

Same shape as §44's stale Gate B: **a probe artefact presents as a finding**,
and both times the tell was a field that made no sense for the chord under
test rather than anything about the chord itself.
