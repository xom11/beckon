Or let beckon hold the keys.

On macOS and Windows nothing binds hotkeys for you, so beckon serve does it itself — a flat TOML, watched for edits, reporting how many of its lines actually registered.

  • macOS

    brew services start beckon is the whole install; the formula ships the LaunchAgent.

  • Windows

    beckon-serve.exe is a tray app with no console window at any point — reload, pause, open the log or open Settings from the tray.

  • Linux

    Deliberately not served here. Your compositor already binds keys better than beckon could, so bindsym $mod+c exec beckon Chrome is the integration.

Install.

No runtime, and no config file for beckon <id> — ids resolve against the OS on every call. Take whichever channel your machine already has.

Homebrew macOS · Linux

brew install xom11/tap/beckon

On macOS the formula also ships the LaunchAgent, so resident mode is one more line. Write ~/.config/beckon/apps.toml and beckon check it first.

brew services start beckon

Scoop Windows

scoop bucket add xom11 https://github.com/xom11/scoop-bucket
scoop install xom11/beckon

That also puts beckon serve in your Start menu. First launch with no config writes a starter apps.toml and opens it in your editor.

Cargo from git

cargo install --git https://github.com/xom11/beckon

Needs Rust 1.75+ and a system C / MSVC toolchain. The binary lands in ~/.cargo/bin/beckon; add --force to update in place.

Nix flake

nix run github:xom11/beckon -- list

To pull beckon into your own flake, add inputs.beckon.url = "github:xom11/beckon" and beckon.overlays.default to your overlays; pkgs.beckon then resolves.

Every release also attaches prebuilt binaries for six targets — x86_64 and aarch64, for Linux, macOS and Windows: github.com/xom11/beckon/releases.

Questions.

Do I need a config file?

Not for beckon <id>. Ids resolve against the OS's own metadata on every call, so there is nothing to generate, no cache to rebuild and no alias file to keep in sync between machines. Only serve reads a file, and that file is a hotkey table — "ctrl+super+alt+t" = "Terminal" — not a place to rename apps.

Why names instead of bundle ids?

Because canonical ids drift and names do not. Brave and Chrome mint a hash into a PWA's id when you install it, so brave-fmpnliohjhemenmnlpbfagaolkdacoja-Default is a different string on your second laptop and the dotfile you copied there silently stops working. The display name is the same on all of them. beckon resolves it against .desktop files on Linux, LaunchServices on macOS and the Start menu on Windows, on every invocation. A canonical id is still accepted, and is the right answer when two apps share a display name.

Why does the demo want a bare letter, and not beckon's real chord?

Because a web page cannot see beckon's real chord on two platforms out of three. Super is taken by the compositor before the browser hears it, Win opens the Start menu, and Caps Lock exposes only its lock state to a page, never a press — which is why the previous version of this page had a readout that said Caps Lock: unknown. Only macOS Hyper (cmd+ctrl+alt) is genuinely observable. Rather than work on one machine and apologise on the other two, the demos ask for the letter alone and print the real chord beside each desk.

Does beckon register the hotkey on Linux?

No — your compositor does, and that is a choice rather than a gap. Every Linux desktop already ships a place to bind a key to a command, and there is no single API that would cover all of them: X11 has XGrabKey, KDE has KWin scripting, Hyprland has the GlobalShortcuts portal, GNOME would need its extension, and sway has no route at all. Four implementations for one feature, on the platform that needs it least. The survey is in CLAUDE.md under Wayland hotkey.

Why does macOS ask for Accessibility?

Raising another application's window goes through the Accessibility API, and macOS gates it behind an explicit grant. The grant is bound to the binary's code signature, so building beckon yourself and rebuilding it can invalidate it and ask again. beckon doctor reports whether the process it is running in is trusted.

What does GNOME Wayland need?

The bundled shell extension from extensions/, plus a log out and back in — Wayland cannot reload the shell live. Mutter gives an external process no way to focus a window at all, so the extension runs inside gnome-shell and beckon talks to it over the session bus. KDE Wayland is the opposite case and needs nothing installed: KWin ships its own scripting engine, so beckon loads a script, reads the answer back and unloads it.

Is it fast?

The whole focus-or-launch path measured about 57 ms on the ARM64 Windows 11 laptop beckon is developed against, and about 95–105 ms on the macOS laptop it is developed against. Each figure is one machine and one run series, not a benchmark suite. The macOS figure is mostly the OS rather than beckon: open -b <bundle_id> alone accounts for 55–75 ms of it, and no API avoids that round trip. The Windows figure has no such breakdown — it started at about 443 ms and came down by changing beckon, not the OS.

What is in the Windows settings window?

Every binding, with whether it actually registered — so a chord another application already owns is visible rather than silently dead. It writes back the same apps.toml you would edit by hand: comments and key order survive, because it edits the document rather than re-serialising it. Ready-to-use setups, including the launchd agent and the Scheduled Task definition, are in examples/macos/serve/ and examples/windows/serve/.

Can I use Caps Lock as the modifier?

On Windows, and it is off by default. Tick the Caps Lock box in Settings and holding Caps stands in for ctrl+super+alt, so CapsT does what ctrl+super+alt+T does — your bindings do not change, and the same file still works on a machine where the box is not ticked. The hook swallows the Caps key itself and sends the chord on as one burst, so the lock does not flip while you use it; tapping Caps on its own still toggles Caps Lock, because beckon puts that keystroke back. keyboard.caps_tap = "escape" makes the tap Esc instead, and "none" makes it do nothing. Three caveats, all real: it does nothing while an elevated window has focus, though typing the chord by hand still works there; any other remapper that already claims Caps — kanata, PowerToys Keyboard Manager, an AutoHotkey script — wins, so use one or the other and not both; and it installs a low-level keyboard hook, the same mechanism every remapper uses and the one antivirus software associates with keyloggers.

Windows is the only place beckon does this itself, and the rows under the hero still print Caps Lock on all three machines because the outcome is the same everywhere — it just comes from somewhere else. On macOS that somewhere is Karabiner-Elements mapping Caps to Hyper, which is where cmd+ctrl+alt comes from in the first place; on Linux it is kanata, an xkb option or your compositor mapping Caps to Super. beckon cannot tell the difference and does not need to: what reaches it is the chord your binding already names, so the same apps.toml and the same sway config keep working whether or not Caps is involved.
